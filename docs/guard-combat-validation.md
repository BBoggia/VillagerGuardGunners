# Guard combat validation

The isolated combat suite records guard movement and native gun activity for
four encounters: a gun exhausting its last round without a backup, a target replacement while using
a sidearm, a reload under pressure from approaching enemies, and retreat with a
wall behind the guard and openings at its sides.

These are development fixtures. They do not change normal guard behavior or run
in the default correctness suite. Their separate namespace and disposable world
prevent other GameTests' configuration changes from affecting the encounters.

## Run observations

Select JDK 17, then run from the project root:

```sh
python3 tools/validate_guard_intelligence.py --mode baseline --offline
```

Omit `--offline` if dependencies need downloading. The runner builds the
production JAR and launches the four scenarios sequentially through the normal
Forge GameTest server. Each scenario observes 180 ticks. The guards retain their
registered goals and target selectors; neither guards nor enemies are pinned or
manually ticked. A single explicit target replacement is the sidearm scenario's
controlled input.

The suite paces its dedicated server callbacks to normal 20 TPS because TaCZ
uses wall-clock action timing. It does not rewrite native cooldown timestamps,
force reload completion, or request weapon swaps directly. The actors have
10,000 health to keep the observation window intact, and Husks have explicitly
configured movement speeds. These encounters establish movement and weapon-state
behavior, not survival rates, combat balance, or server performance.

Results are retained in a unique directory under `build/reports/guard-intelligence/`:

- `manifest.json`: source hashes, Git state, dependency metadata, artifact hashes,
  command, exit status, scenario summaries, and evidence hashes.
- `gradle.log`: the complete runtime result, including setup or assertion failures.
- `scenarios/`: per-tick positions, active goals, reload state, ammo observations,
  sidearm transitions, and planned acceptance results.
- `runtime-config/`: the configuration generated by that isolated run.

The runner requires exactly four completed, valid scenarios. A Gradle invocation
that discovers zero tests is not a successful observation. Missing reports,
partial windows, incorrect modes, and source changes during a run invalidate the
evidence. Run the wrapper sequentially with other Gradle runtime tests; its lock
excludes another instance of this wrapper, not unrelated Gradle invocations.

## Exercise the planned behavior contracts

```sh
python3 tools/validate_guard_intelligence.py --mode acceptance --offline
```

This uses the same fixtures and additionally asserts these desired outcomes:

| Encounter | Acceptance |
| --- | --- |
| Empty gun | No upstream melee pursuit, at most 0.75 blocks of forward displacement, and at least 2 blocks of guard movement ending at least 8 blocks from surviving enemies. |
| Sidearm target replacement | The usable sidearm remains active while the primary remains empty. |
| Reload pressure | At most 0.75 blocks of positive X travel while reloading within 16 blocks of enemies; at least 1 block of first-reload withdrawal with at most 5 first-reload samples within 6 blocks of enemies. |
| Wall retreat | At least 10 samples behind the wall's X plane with at least 6 blocks of enemy separation. |

The acceptance mode is intentionally separate while the behavior is being
implemented. A baseline result of `observed` means the fixture worked; it does
not mean these acceptance checks passed. The manifest records their individual
boolean results. `acceptance_failed` returns a nonzero process status and retains
the full observations. A fixture/setup failure is `invalid_evidence`, which must
be investigated before interpreting any behavior result.

Normal correctness tests require dry and invalid-window guns to retain defensive
ownership. They also cover ammo arriving during the retry window, native reload
cancellation with usable reserves, explicit Fall Back commands while dry, and
sidearm continuity across target replacement, inventory-fed recovery, chamber and
manual-bolt readiness, and unreadable metadata recovery. The moving encounters retain their
full withdrawal requirements alongside the threat-assessment and route-planning tests.

## Fixture interpretation

The open-floor encounters place enemies along the guard's positive X direction.
Forward movement metrics therefore measure the guard's own displacement toward
that group, separately from enemies approaching it. Reload movement records
positive X travel during native reload samples within 16 blocks of an enemy.
The wall fixture verifies that a native escape path exists without assigning it
to the guard. Goal activity and actual position changes establish behavior;
merely releasing a goal or selecting a movement label is insufficient.

These are narrow contracts for the controlled layouts. Separate route planning tests
cover detours, hazards, multiple attack directions, command boundaries,
and legitimate temporary movement toward a threat to escape an obstruction.
Do not generalize the fixture's X-axis metric into production movement policy.

Direct development invocation is also available:

```sh
./gradlew runGameTestServer -PguardIntelligenceTestMode=baseline
```

The wrapper is preferred for retained evidence. Direct invocation uses a reusable
report directory and does not create an identity manifest. Both modes reset only
`build/guard-intelligence-runtime`, never ordinary development or player worlds.


## Integrated client on generated terrain

After the full automated matrix has produced version-matched world metadata,
select JDK 17 and run:

```sh
python3 tools/run_guard_combat_client_qa.py
```

This compiles an isolated QA source set and exports the Forge development-client
launch. It then opens a fresh normal Overworld with seed `314159`; no existing
world chunks or player data are copied. The harness selects gently sloping grass
terrain and makes no terrain edits. Loaded firing, an empty gun without a backup,
reload pressure, and a usable sidearm each run for 300 server ticks. Targets move
normally; invulnerability keeps the observation window intact. Orders change to
Hold Position and Hold Fire near the end of each scene.

Each timestamped directory under `build/combat-client-qa/` contains server
assertions, client and server entity samples, screenshots, and a manifest of the
production artifact, sources, loaded development classes/resources, and harness.
The runner requires completed server assertions, client movement and weapon
observations, and all four screenshots. Inspect screenshots as well as the
machine-readable result. These are development-class observations associated with
a built production artifact, not an installed-JAR compatibility test.

Run this sequentially with Gradle validation and outside performance measurements.
The spectator camera turns toward the observed guard each tick so a long retreat
remains in view; it does not reposition the guard or change its movement.

The integrated run does not start a dedicated server or alter EULA acceptance.
Dedicated-server testing with two independent observers remains a separate check.
See [Tactical tuning](guard-tactical-tuning.md) for defaults and limits.
